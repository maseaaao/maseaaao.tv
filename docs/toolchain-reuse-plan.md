## Вывод

Сохранить npm workspaces и расширить существующий `@maseaaao/design`. Выделять пакет UI и пакет конфигураций сборки после подтверждения повторяющегося контракта у двух потребителей. Использовать Vite для браузерных приложений, PostCSS для самостоятельных CSS провайдеров, Playwright и Sharp для изображений. Подключить Prettier, ESLint, typescript-eslint, html-eslint и Stylelint.

Пакеты со шрифтами и CSS могут экспортировать исходные ресурсы напрямую: отдельная сборка каждому внутреннему пакету не нужна. Сборщик нужен потребителю, чтобы разрешить импорты, собрать зависимости и сформировать нужный формат публикации.

## Границы внутренних пакетов

| Пакет                                                        | Ответственность                                                                                                                     | Потребители                                          |
| ------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------- |
| `@maseaaao/design` — расширить существующий                  | Unbounded WOFF2/TTF, OFL, font-face, палитра, семантические CSS-токены                                                              | Сайт, Stream Info, Tuna, OBS CSS/HTML, artwork       |
| `@maseaaao/ui` — условный этап после инвентаризации повторов | Общие CSS-примитивы: button, field, card, badge, focus, visually-hidden; составные DOM-компоненты только при подтверждённом повторе | Собственные браузерные интерфейсы; выборочно artwork |
| `@maseaaao/build-config` — выделить после пилота двух сборок | Функции конфигурации Vite для сайта/автономного HTML, конфигурация PostCSS, минимальные адаптеры форматов                           | Только build/dev tooling приложений                  |

До создания `ui` составить таблицу конкретных совпадений: компонент, два потребителя, разметка/семантика, состояния, клавиатурное поведение и допустимые различия. Визуально похожих карточек недостаточно для общего компонента. Если общего контракта нет, оставить локальную реализацию, использующую `design`. Не переносить бизнес-логику в пакет ради уменьшения числа строк приложения.

Общий build preset выделять из двух работающих конфигураций. Browser build config не импортируется в runtime; зависимости на Vite/PostCSS остаются в dev/build-области. Пакеты имеют разрешённое направление зависимостей: приложения → ui → design; build-config не зависит от приложений. Проверять запрет импортов внутренних src другого приложения.

У внутренних пакетов задать `private`, `version`, явные `exports` и зависимости потребителей. Для текущего npm использовать совместимые version ranges локальных workspaces, а не переносить синтаксис другого менеджера пакетов. CSS отмечать как side effect, если в пакете задаётся `sideEffects`.

Разделить текущий `brand.css` на `fonts.css`, `tokens.css` и совместимый агрегирующий entrypoint. Шрифтовые файлы и лицензия имеют один редактируемый источник. Токены общие, layout конкретных сцен и приложений остаётся у владельца.

CSS-компоненты должны иметь явные классы/контракт и минимальное влияние на окружение. CSS провайдеров не получает общий reset и стили собственных форм целиком: используются только нужные токены и шрифт. Глобальные стили не должны переопределять DOM Streamlabs/DonationAlerts случайно.

Сборщик сам по себе не создаёт систему компонентов. На первом этапе `ui` даёт общие стили и небольшие типизированные функции для действительно одинакового DOM-поведения. Вынесение каждого похожего фрагмента HTML в собственный шаблонизатор не требуется. Если при декомпозиции обнаружатся повторяющиеся составные элементы с состоянием, отдельно выбрать готовую компонентную модель и проверить её на двух потребителях. Перевод всех продуктов на Vue/React/Astro в этот план не включён.

## Инструменты и решения

| Задача                        | Решение                                                                                    | Что заменяет / ограничение                                                                                                                                         |
| ----------------------------- | ------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Сайт с несколькими страницами | Vite, несколько HTML entrypoints, отдельные CSS/JS/WOFF2 assets                            | Ручное копирование ресурсов и шрифта. Сохраняет публичные маршруты и файлы Cloudflare                                                                              |
| Автономные HTML               | Vite + уже используемый `vite-plugin-singlefile`                                           | Regex-сборщик Tuna и внедрение base64 в исходники. Отдельная сборка на каждый HTML: singlefile не предназначен для нескольких HTML entrypoints одновременно        |
| Самостоятельные CSS           | PostCSS CLI + `postcss-import` + `postcss-url`                                             | Ручное раскрытие импортов и font URL. Настроить inline для WOFF2 и сохранить лицензию                                                                              |
| JS/TS lint                    | ESLint flat config, `@eslint/js`, `globals`, `typescript-eslint`, `eslint-config-prettier` | Раздельные browser/Node/ESM/CommonJS области; type-aware правила для TS-проектов                                                                                   |
| HTML lint                     | `@html-eslint/eslint-plugin` и parser                                                      | Проверки разметки и базовой доступности, в том числе шаблонов при поддерживаемом синтаксисе                                                                        |
| CSS lint                      | Stylelint + `stylelint-config-standard`; `postcss-html` для оставшихся style-блоков        | Проверки CSS отдельно от форматирования                                                                                                                            |
| Форматирование                | Prettier                                                                                   | JS/MJS/CJS/TS/CSS/HTML/JSON/Markdown; отдельная команда, без запуска Prettier внутри ESLint                                                                        |
| Рендер изображений            | Существующие Playwright + Sharp                                                            | Один небольшой адаптер screenshot/export вместо двух циклов. Геометрия сцен и параметры бренда остаются данными проекта                                            |
| ICO                           | `png-to-ico` после проверки установки/поддержки                                            | Ручная запись заголовков бинарного ICO. Более широкий `favicons` нужен только при необходимости полного набора и manifest-генерации                                |
| Companion build/package       | Прототип официального `@companion-module/tools`                                            | Собственная JS-упаковка и два tgz-скрипта. Сначала проверить включение EXE/DLL, лицензию, manifest, Node22 и установку; сборка C# остаётся отдельным Windows-шагом |
| Копирование обычных файлов    | Стандартный `node:fs`, в том числе `cp`                                                    | Не добавлять npm-зависимость для рекурсивного копирования                                                                                                          |

Проверены актуальные registry metadata и официальные документы основных инструментов. Текущий Node 22.20+ подходит проверенным версиям. Перед внедрением зафиксировать совместимую матрицу versions/engines/peerDependencies и проверить чистый `npm ci`; metadata не заменяют тестовую установку. Сначала унифицировать сборки на имеющемся Vite 6.4.3, затем отдельным изменением рассмотреть Vite 8. Не совмещать обязательный архитектурный перенос с обновлением всех major-версий.

## Порядок реализации

### 1. Зафиксировать контракт результатов

- Составить список entrypoints и артефактов: корневой `dist`, два автономных HTML, CSS/HTML виджетов, сцены/обои/баннеры/иконки, пакеты Companion.
- Зафиксировать публичные URL, имена автономных файлов, пути назначения `sync:local`, размеры изображений и прозрачность.
- Сохранить эталонные screenshots основных интерфейсов и тестируемые параметры поведения. Для screenshot-сравнения закрепить Chromium, ОС и шрифтовую среду.
- Зафиксировать, какие файлы являются исходниками, какие — отслеживаемыми экспортами, какие — временными build-файлами.

Критерий: каждому результату соответствует один владелец и однозначная команда сборки. Перед каждым переносом проверить актуальный HEAD и учесть новые изменения после этого аудита.

В таблице контрактов отдельно перечислить:

| Продукт     | Итоговый контракт                                                                                                                                                                   |
| ----------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Website     | Корневой `dist`; все текущие HTML-маршруты, `_headers`, `/.well-known/*`, robots/sitemap при наличии, manifest и иконки                                                             |
| Stream Info | `apps/stream-info/dist/change-info-streamer-bot.ru.html`; один HTML с лицензией и встроенными статическими зависимостями; `streamerbot-import.txt` отдельным процессом              |
| Tuna        | `apps/tuna-widget/dist/obs-tuna-widget.html`; один HTML со встроенными статическими зависимостями и OFL                                                                             |
| OBS widgets | Новый `apps/obs-widgets/dist` содержит social-strip, output-stats, provider CSS/HTML/JS и статические transparent.png/звуки; точные имена и структура соответствуют карте установки |
| Artwork     | Сохраняются конечные пути `artwork/.../rendered`; промежуточные HTML/CSS — в `.build-cache/artwork`                                                                                 |
| Companion   | Существующие ID/manifest/runtime и полный состав EXE/DLL/HELP/license; сборка Windows и проверка архивов обязательны                                                                |

Для каждого старого файла выписать source → build output → существующий путь установки. Переносить `sync:local` вместе с продуктом; отдельно сохранить transparent.png, sounds и другие ресурсы, которые не попадают в JS/CSS dependency graph.

### 2. Проверить технические решения короткими прототипами

- В отдельном временном каталоге собрать Tuna из отдельных HTML/CSS/JS, импортирующих Unbounded через workspace-пакет. Проверить `file://`, загрузку WOFF2, наличие полной OFL, кириллицу, отсутствие внешних статических файлов и неизменность query-параметров. Функциональные обращения к локальному Tuna API проверять подставными ответами; автономность не запрещает предусмотренные сетевые API.
- Собрать один provider CSS через PostCSS: разрешение импорта из design, inline WOFF2, сохранение лицензии и окончательных `{font_size}`/`{message_hide_delay}`. Сравнить финальные селекторы и значения с исходным контрактом.
- Не менять production entrypoints до прохождения прототипов. Зафиксировать совместимые версии и результаты; после этого подключать общий preset к продуктам.
- Оценить внешние пакеты: канонический репозиторий, лицензия, deprecated/status, поддерживаемые Node/peerDependencies, недавняя история сопровождения либо обоснованная стабильность, релевантные открытые проблемы. Популярность и существование свежего номера версии не являются проверкой качества. Проверить чистый npm ci и применимые известные уязвимости.

Критерий: два пилота собраны готовыми инструментами; остаточная проектная обвязка перечислена и обоснована. Если прототип требует нового самописного универсального сборщика, пересмотреть решение до основной миграции.

### 3. Подключить инструменты качества

- Добавить корневые конфигурации ESLint, Prettier, Stylelint, `.editorconfig` и настройки редактора.
- Отдельно описать `.js`, `.mjs`, `.cjs`, browser/Node globals, тесты и TypeScript-проекты. Не объявлять все файлы одновременно browser и Node.
- В этом этапе настроить проверку доступных исходных файлов. Inline JS/CSS переносить в отдельные файлы одновременно с заменой сборки соответствующего продукта на этапе 5: текущий сборщик Tuna не встраивает внешний JS. HTML-линтер сам по себе не проверяет JS внутри script; временные пробелы покрытия перечислить явно и закрыть при переносе, не считать их проверенными.
- Исключить generated outputs, base64-экспорты, импорты Streamer.bot, vendor-файлы и бинарные ресурсы. Для намеренно ошибочных фикстур исключать только применимую проверку, сохраняя форматирование и остальные валидные проверки. Списки исключений соответствуют контракту из этапа 1; временные исключения конкретных смешанных файлов удалить в этапе миграции их владельца.
- Выполнить механическое форматирование отдельным коммитом. Исправления реальных lint-ошибок — отдельно; не выключать правила массово ради зелёного результата.
- Добавить `format`, `format:check`, `lint`, `lint:fix`, `typecheck`. В CI — проверки без автоматической записи файлов.

Критерий: охваченные исходники проверяются из корня, formatter и lint не конфликтуют, lint успешен с `--max-warnings=0`; окончательная полнота покрытия — критерий этапа 7. Выбранные strict TS-правила не допускают `any`, non-null assertions и неподтверждённые приведения как способ обхода типов.

### 4. Оформить общий дизайн и типографику

- Расширить exports `@maseaaao/design`, прописать прямые зависимости потребителей.
- Перенести импорты ресурсов на имена пакетов; убрать зависимости от количества `../`.
- Создать `@maseaaao/ui` только для примитивов с подтверждённым общим контрактом из инвентаризации; иначе этот шаг пропустить. Визуально одинаковые состояния должны пользоваться общими токенами.
- Удалять копии font-face и токенов только после переключения соответствующего потребителя.
- Сохранить полный набор символов Unbounded, вес 600 и OFL. Сайт получает отдельный локальный WOFF2 с кешированием; автономные HTML/CSS — встроенный ресурс.
- Сохранить существующую регенерацию WOFF2 через fonttools: она превращает variable TTF в статический вес и проверяет Unicode-покрытие. Обёртка npm поверх Python не уменьшит сложность.

Критерий: замена канонического WOFF2 или токена меняет все необходимые результаты при штатной сборке; исходники потребителей не содержат сгенерированный base64.

### 5. Унифицировать сборки приложений и CSS

- Выделить `@maseaaao/build-config` из успешных пилотов. Сначала перенести Tuna, затем Stream Info, provider CSS/OBS-виджеты и сайт. Конфигурации остаются короткими и явными. Для каждого продукта выделение inline-кода, новая сборка, изменение путей, адаптация тестов и CI составляют один проверяемый этап.
- Перевести сайт на Vite MPA: редактируемые HTML/CSS/JS — в source-каталоге, неизменяемая статика — в public. Сохранить `_headers`, `/.well-known/*`, manifest, favicons и все текущие страницы, включая `/tools`. Проверить каждую вложенную страницу прямым открытием по HTTP, ссылки, base и asset URLs.
- Зафиксировать стратегию URL: публичные маршруты страниц и явно используемые внешними потребителями файлы сохраняются; внутренние bundled CSS/JS/WOFF2 получают content hash. Пересмотреть `_headers`: immutable-кеш только для хешированных ресурсов, HTML и ресурсы с постоянным URL продолжают ревалидироваться. Старые правила `/assets/site.css` и `/assets/fonts/*` не считать автоматически подходящими новым именам.
- При переводе classic scripts сайта/виджетов в modules проверить момент выполнения, DOM ready, область видимости и используемые globals. Не менять runtime target без проверки совместимости с OBS CEF и браузерами проекта.
- Перевести Tuna на Vite + singlefile. Сохранить query-параметры, тайминги, retry limits и автономную загрузку через `file://`/OBS.
- Подключить Stream Info к общему preset. Использовать поддерживаемый `outputFileName` singlefile вместо отдельного скрипта переименования; проверить чистую очистку output и нормализацию EOL.
- В OBS-виджетах выделить `src` и `dist`; standalone HTML собирать отдельно, CSS провайдеров — PostCSS. Обновить тесты и `sync:local`, сохранив пути установки в рабочих приложениях.
- Для Streamlabs держать исходный CSS синтаксически корректным. Provider placeholders выпускать на финальном шаге явной заменой ограниченного набора маркеров после всех CSS-преобразований. Зафиксировать точные ожидаемые подстановки и их количество; проверять отсутствие промежуточных маркеров и сохранность окончательных placeholder-значений. Линтить исходный CSS; финальный шаблон проверять также после подстановки безопасных тестовых значений. Не менять анимации/длительности провайдера.
- Для каждого singlefile-build использовать отдельный принадлежащий ему output/staging-каталог. Перед очисткой проверять его владельца. При агрегировании нескольких HTML один запуск не должен удалять результаты другого; проверить обе последовательности сборки и повторный запуск.
- Не считать наличие singlefile-плагина доказательством автономности. Ресурсы из public могут остаться внешними. Проверять итоговые script/link/img/srcset/CSS url и file://-загрузку с учётом явно разрешённых runtime API/контента. Проверять отсутствие посторонних файлов/дублирующихся font-face, размер HTML и точные байты встроенного WOFF2 и лицензии.
- Сохранить CSP-контракт каждой среды: singlefile может требовать разрешения inline-script/style и data:font. Не ослаблять CSP провайдера или сайта автоматически; неподдерживаемый вариант считать ограничением миграции. Проверка реальной CSP провайдеров требует отдельной приёмки в их окружении.
- Удалить `prepare-inline-design.mjs`, ручной HTML/CSS inlining Tuna и копирование дизайна в website source после подтверждения новых результатов. Любой дополнительный hook оставить только для специфической обязанности, например сохранения лицензии в одиночном HTML.
- Изменить build graph: сборка сайта собирает сайт; сборка виджетов — виджеты. Текущие `/tools/stream-info.html` и `/tools/tuna-widget.html` — информационные страницы, а не copies автономных приложений: не добавлять их размещение как новую функцию. Если появится обоснованная публикационная зависимость, описать её отдельно.
- Одновременно с каждым переносом заменить проверки source=dist на проверки маршрутов, ресурсов, поведения и повторяемости новой сборки. Сохранить предметные инварианты из `check-repository.mjs`/`migration-contract.mjs`, адаптировав пути и область обхода; `.build-cache`, generated outputs и source проверяются по своему назначению. Не откладывать эту адаптацию до финального этапа.

Критерий: сборки читают исходники и пишут только разрешённые outputs. Сборка одного приложения не переписывает исходники другого. Повторная сборка не создаёт diff отслеживаемых текстовых артефактов.

### 6. Сократить генераторы; декомпозиция поведения — отдельно

- Описать render jobs данными: source URL, output, viewport, scale, format, alpha/quality. Один адаптер Playwright ждёт шрифты/изображения и передаёт PNG в Sharp.
- Рендерить подготовленные страницы через контролируемый локальный сервер, если Vite outputs используют modules; доступ к внешней сети запрещён, локальный build origin разрешён. Автономные HTML отдельно проверять через `file://`.
- Вынести исходный CSS сцен из JS-строк в CSS-файлы. Текущий `layout.json` сохранить источником геометрии. Generated HTML размещать во временном build-каталоге; итоговые изображения сохраняют рабочие пути `artwork/.../rendered`.
- Заменить ручную сборку ICO готовым кодировщиком. Не менять размеры, маску и состав опубликованных иконок без отдельной задачи.
- Оставить Sharp для ресайза, компрессии и alpha; qrcode/jsQR — для генерации и проверки читаемости. Сохранить проектные проверки QR с логотипом на малых размерах.
- Декомпозицию `main.ts` Stream Info вынести в отдельный последующий рефакторинг: transport/state/storage, category picker, template editor, modal, rendering. Она не является условием миграции сборок. Сохранить API version, localStorage keys, импорт C#, таймауты, кеш 5 секунд и его сброс после записи. Общий компонент выделять только по подтверждённому контракту.
- Выделить миграцию Companion toolchain в независимый подпроект после браузерной инфраструктуры. Проверить официальный инструмент на одном модуле, затем перенести второй. Если EXE/DLL или формат установки не поддерживаются штатно, зафиксировать ограничение и оставить небольшой общий адаптер упаковки вместо двух копий. Защитные проверки состава архива сохранить.

Критерий основного этапа: один путь screenshot/export, проверенный ICO-кодировщик, сохранённые геометрия, QR, alpha и размеры. Для независимой миграции Companion — единая упаковка и проверенный состав Windows helpers; её недоступность не блокирует приёмку завершённой браузерной инфраструктуры.

### 7. Финальная приёмка CI и документации

- Linux: clean `npm ci`, format/lint/typecheck, unit/browser tests, все браузерные/CSS сборки, проверка outputs и лицензий.
- Windows: compile helpers, Companion build/package, `test-packages.py`. Проверять именно окончательный commit SHA.
- Проверить итоговую полноту уже перенесённых тестов: запуск из clean checkout действительно собирает нужные артефакты до тестов; тесты читают outputs, а не старые или временные копии. Игноры линтеров не оставляют собственные исходники непроверенными.
- Сохранять побайтовую повторяемость текстовых результатов. Для raster screenshots использовать закреплённую render-среду и утверждённый visual diff; перенос toolchain может дать обоснованное первоначальное отличие сжатия/пикселей.
- Обновлять `AGENTS.md`, README, architecture, local-installation и CI-команды вместе с переносом каждого владельца; здесь сверить конечную согласованность всех путей и команд. Общая команда build:all перечисляет явные зависимости; порядок полей workspaces не использовать как неявный планировщик. Пересмотреть `full`, чтобы он не выполнял повторную сборку сайта по исторической причине.
- Форматирование, линт, общий дизайн, перенос каждой сборки и замены генераторов разделить на обозримые коммиты. Часть инфраструктуры проверять постепенно, без одного большого переписывания.

Критерий: новая чистая копия собирается документированными командами; каждый build output воспроизводим в своей среде; изменения ресурсов не маскируют необходимость установки в OBS/Companion.

## Что сохраняется и что отложено

Сохраняются npm workspaces, независимые версии продуктов, Node22 для Companion, утверждённый логотип, геометрия OBS, форматы автономных файлов и провайдерские события. Nx/Turborepo, отдельный сборщик библиотек, Tailwind и переход всех приложений на общий UI framework пока не требуются: текущий масштаб обслуживают явные workspace-команды. Build cache имеет смысл оценивать по времени новой сборки, а не вводить заранее.

Рабочие приложения, базы, кнопки, Action ID, звук и эфир эта инфраструктурная задача сама по себе не меняет. Применение собранных ресурсов остаётся отдельным шагом с проверкой назначения и резервированием.
