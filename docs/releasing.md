# Независимые выпуски

Stream Info, Tuna, OBS Widgets, Artwork, System Microphone, VoiceStream, Windows-интеграции и сайт выпускаются независимо. Префиксы тегов: `stream-info-v`, `tuna-widget-v`, `obs-widgets-v`, `artwork-v`, `system-microphone-v`, `voice-stream-v`, `windows-integrations-v`, `website-v`; далее строгая версия `X.Y.Z`. Изменять версию продукта и CHANGELOG. Модули Companion требуют согласованной версии package.json/manifest.json. У сайта и Windows-интеграций версия хранится отдельно в `release-version.json` / `version.json`; корень монорепозитория общей версии не имеет. Lockfile обновлять только когда это требуется изменениями зависимостей/workspaces.

Выпускаемые продукты объявлены в `tooling/release-products.json`: для каждого — префикс тега, каталог, состав артефактов, команды проверки и сборки, а также явные признаки `dotnet`, `browser` и необязательный путь `pythonRequirements`. Workflow не знает о конкретных продуктах: тег разбирает `tooling/release-product.mjs`, а состав архива — `tooling/package-release.py`. Добавление нового продукта — это запись в манифесте, шаблон тега в workflow и контрактный тест `tests/release-products.test.mjs`, который требует их согласованности.

Для локального dry-run сначала явно установить необходимые инструменты: Node/Bun, Python; .NET только Stream Info/Companion, Chromium только Tuna/Artwork, font requirements только Artwork. `release-product.mjs` больше не устанавливает prerequisites внутри build. После проверки исходников выполнить `python tooling/package-release.py --validate <тег>`, `node tooling/release-product.mjs <тег>`, затем `python tooling/package-release.py <тег>`. Результаты находятся в `build/release/<тег>`: полный ZIP продукта, `<тег>.manifest.json`, `SHA256SUMS`, `windows-updater.zip` и notes.md. У Stream Info и Tuna также сохраняются отдельные HTML для ручного скачивания с прежними именами. Stream Info включает импорт C#. Artwork запускает рендер окончательных изображений, а не только промежуточных HTML. Независимые каталоги результатов позволяют упаковать несколько продуктов без удаления соседних пакетов.

Манифест пакета содержит schemaVersion/runtimeLayout, продукт, версию, тег, commit, точные пути/размеры/SHA256 файлов и архива, указания по подключению и `requires`: минимальные стабильные версии других устанавливаемых продуктов. Пустой `requires` означает отсутствие объявленных зависимостей между пакетами, а не подтверждение их совместной приёмки. Локальные сборки с незакоммиченными правками годятся для проверки упаковки; официальный релиз собирается workflow из тега. Bootstrap обновлятора содержит код и каталог продуктов из того же коммита.

После явного решения о выпуске отправить тег. Workflow выполняет `plan → build → draft`: до Bun install проверяет существующий `refs/tags/<тег>`, версию и CHANGELOG, фиксирует SHA, собирает продукт **до** dist-зависимых тестов и упаковывает его с read-only permissions. Отдельный job получает обязательный artifact этого же run, валидирует точный набор файлов/контрольные суммы/архивы/commit, затем с ограниченным по шагам `GH_TOKEN` создаёт draft через `--verify-tag`, читает его обратно, скачивает в `build/downloaded/<тег>` и побайтно сверяет все ассеты. Отсутствующие и лишние файлы, перемещённый тег, существующий релиз и ошибка API блокируют дальнейшее выполнение. Для продуктов, требующих браузер, устанавливается Chromium с системными зависимостями; Artwork также устанавливает закреплённые Python-зависимости рендера. Существующие выпуски не перезаписываются. Это ограничение workflow, а не обещание включённой в GitHub настройки immutable releases.

По тегу workflow оставляет **проверенный draft**. Обычно публиковать его вручную после проверки скачанного HTML в OBS. Для заранее разрешённого выпуска ручной `workflow_dispatch` принимает флаг `publish` (по умолчанию `false`): отдельный шаг `promote` после download verification публикует только новый draft с receipt этого run и проверяет состояние по точному release ID. Повторный dispatch не продвигает ранее существующий draft и не перезаписывает его; при сбое проверки черновик оставляется для диагностики, автоматического удаления нет. Общий releases/latest объединяет разные продукты; давать ссылки на конкретные теги. Исторический change-info-streamer-bot хранит прежнюю историю и выпуски; разработка ведётся здесь.

Для остальных продуктов проверять соответствующие изображения/архивы и результат штатного подключения. Старые HTML-релизы без нового манифеста остаются доступны вручную; обновлятор требует новый выпуск, старые ассеты не дописываются. В Windows доступны установка одного продукта, **всех последних стабильных продуктов** и закреплённого комплекта версий: [инструкция обновлятора](windows-releases.md). Публикация продукта не запускает обновление пользовательского стрима.

Проверки инфраструктуры: `bun run test:releases`. Они проверяют каталог, упаковку бинарных файлов, план без записи, все последние версии, контрольные суммы, зависимости, сохранность текущей установки при сбое второго пакета, откат, восстановление после прерывания и блокировку параллельного запуска. Выполняются в Linux CI без запуска приложений стрима.


## Интерфейс pipeline

```bash
# Только в checkout самого существующего тега; до workspace install:
node tooling/release-product.mjs --plan <тег>
# После явной установки prerequisites:
node tooling/release-product.mjs --build <тег>
python tooling/package-release.py <тег>
python tooling/package-release.py --verify-package <тег> --commit <SHA>
```

`--plan` возвращает JSON и scalar GitHub outputs `tag`, `sha`, `product`,
`dotnet`, `browser`, `pythonRequirements`. Старый вызов `<тег>` остаётся alias
build+test. Режимы `--draft <тег> --sha <SHA>` и `--promote <тег> --sha <SHA>`
выполняют сетевые **записывающие** операции и не относятся к dry-run; без явного
разрешения на публикацию локально их не запускать. Contract tests используют
подставной `gh`, без обращения к эфиру или GitHub writes.

Тег для нового pipeline должен указывать на commit с этой инфраструктурой.
Старые теги/ассеты не переписываются задним числом. Сайт упаковывается как
статический продукт: выпуск не запускает публикацию Cloudflare и не обновляет
Windows runtime. Полный DAG, кеши и локальные ограничения — [CI/CD](ci-pipelines.md).
