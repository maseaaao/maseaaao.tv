# Ранняя проверка автономного UI

Технический образец этапа 2, не продукт и не установка в OBS. Цель — проверить Vue SFC + TypeScript + текущие Vite/singlefile на настоящем `file://` с внешним подставным WebSocket. Полного общего окружения компонентов/Storybook пока нет — это этап 4.

Из корня с Node 22.20+ в ветке 22:

```sh
npm ci
npm run test:ui-probe
```

Для установленного Chrome задать `CHROME_BIN`. Итоговый файл: `.build-cache/ui-portability/ui-portability.html`. Его можно скопировать в пустой каталог: CSS, JS, Unbounded 400 и OFL встроены. Файл не требует сервера UI. Тестовый endpoint существует только на loopback во время теста; рабочие Streamer.bot/OBS не используются.

## Зафиксированная цепочка

Vue 3.5.44, @vitejs/plugin-vue 5.2.4 (peer Vite 5/6), Vite 6.4.3, vite-plugin-singlefile 2.3.4, TypeScript 5.8.3, vue-tsc 3.0.8. Vue и ws 8.22.0 выбраны с исправлениями относительно ранних patch-версий; major Vite не менялся. Новые зависимости изолированы в tooling workspace, lockfile один.

Основание: [официальный Vue tooling](https://vuejs.org/guide/scaling-up/tooling.html), [релиз Vue](https://github.com/vuejs/core/releases/tag/v3.5.44), [релиз ws](https://github.com/websockets/ws/releases/tag/8.22.0); совместимость plugin/Node проверена по metadata npm и реальной сборкой. Клиент — прежний @streamerbot/client 2.0.1. Его template compiler не входит в клиентский результат; SFC компилирует официальный plugin.

## Проверяемый сценарий

Тест создаёт пустой каталог и отдельный persistent Chrome profile. Полный сценарий: file → ввод порта → Hello с salt/challenge → Authenticate с SHA-256 → GetEvents/Subscribe → форма → DoAction acknowledgement → отдельный Custom.CodeEvent → ответ. Подставной сервер принимает только `Origin: null`; проверяются отказ origin, повторное подключение и повтор после закрытия socket. Никакие реальные Actions не выполняются. Пароль `probe-only` — публичное тестовое значение, не секрет и не пароль приложения пользователя.

Настройки образца имеют отдельный ключ `maseaaao.ui-portability.v1`. Тест закрывает браузер целиком и запускает тот же профиль заново: значения по прежнему абсолютному пути восстанавливаются. Смена пути проверяется отдельно и записывается как наблюдение, без обещания переносимости. Неверный settings JSON проходит runtime guards, не assertions. Таймер ожидания ответа очищается на ответ, ошибку и disconnect/unmount; поколение соединения защищает от устаревших callbacks.

## CSP: явная разница с текущей статистикой OBS

Образец сохраняет nonce для script/style, запрет inline handlers/атрибутных стилей, default-src none и `require-trusted-types-for 'script'`. Разрешает только loopback WebSocket как источник данных. Единственная необходимая адаптация Trusted Types — `trusted-types vue` вместо строгого варианта `trusted-types 'none'` контрольной fixture. Vue создаёт именованную policy для статической разметки. Тест сначала требует отсутствие CSP violations в рабочем варианте, затем отдельно подставляет прежнюю none-policy и доказывает конфликт по securitypolicyviolation. Он не снимает Trusted Types и не разрешает eval/unsafe-inline.

До переноса статистики в этапе 6 отдельно проверить этот узкий policy diff и отсутствие v-html/недоверенного HTML в потребителях; текущая CSP продукта в этом этапе не меняется. Этот образец не доказывает совместимость всех будущих компонентов или clipboard/storage API OBS.

## Свежая проверка 19.10.2026

macOS, Node 22.22.3, Chrome 153.0.8010.52: сборка/проверка SFC и тест полного сценария прошли. Итоговый HTML — 255127 байт, без gzip. Нет запросов HTTP за UI-ресурсами, шрифт загружен, pageerror отсутствуют в положительном сценарии; origin denial проверяется отдельно. На этой версии Chrome настройки при другом file-path тоже оказались доступны: это наблюдение конкретного профиля, а не переносимый контракт.

Номер времени в диагностике теста включает пользовательские взаимодействия; он не является измерением startup и не задаёт бюджет. Окончательные бюджеты и обязательная CI-интеграция — этап 4.

Windows 11 / Chrome и обе формы использования в OBS не проверены. Пустые чекбоксы допроверки находятся в [плане](../../docs/ui-renewal-plan.md). По уточнению пользователя их отсутствие не блокирует доступные следующие работы, но не означает итоговую приёмку.
